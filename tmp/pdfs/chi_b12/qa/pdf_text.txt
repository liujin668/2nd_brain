B12.1 引言
内存标签扩展（Memory Tagging Extension，MTE）是一种用于检查内存中所存数据是否被正确使用的机制。当某
个内存位置被分配用于特定用途时，也可以为其指定一个内存标签。该内存标签与对应数据一同保存在内存中，称为
分配标签（Allocation Tag）。以后访问该内存位置时，请求方同时使用该位置的地址，以及请求方认为与该位置关
联的标签值。此标签称为物理地址标签（Physical Address Tag）或物理标签（Physical Tag）。
对于启用了标签检查的任何访问，都会将物理标签与分配标签进行比较。访问始终正常进行，而标签检查的结果决定
是否报告错误情况。

MTE 确保内存访问符合其预期用途，而不是错误或恶意访问。MTE 可在运行时识别许多常见的程序内存错误，例如
缓冲区溢出和释放后使用。
内存中每个按 16 字节对齐的 16 字节数据块，都关联一个 4 位的内存标签。
支持以下行为：
 仅允许在面向 Normal WriteBack 存储器的请求中使用内存标签。
 读事务在事务请求中包含一项指示，用于确定是否必须随数据一起返回分配标签值。
由请求方执行返回的物理标签与分配标签之间的检查。

如果缓存中保存了数据值，但未保存分配标签值，则必须执行同时返回数据和标签的读事务。返回的数据不要求有效。
 需要获取标签的读请求不得使用 Forwarding snoop（转发侦听）。
 请求分配标签的 StashOnce 事务。预期分配标签随数据的 stash 操作一起被存入。
 随写数据一起提供物理标签、且该物理标签必须与分配标签进行比较的写事务。

 将分配标签更新为新值的写事务。
这些写事务通常同时更新数据。不过，允许令 BE=0，从而仅更新标签。
 将 Dirty 或 Clean 缓存行传递到下游缓存或内存控制器、且既不更新也不检查标签的写事务。这些写事务始终包
含数据，并提供一项指示，说明是否也随数据传递分配标签值。如果标签为 Clean，则可以选择是否在写事务中提
供这些标签。
 返回数据的侦听事务也可以返回关联的分配标签。如果标签为 Dirty，则必须返回。如果标签为 Clean，则可以选
择是否返回。
 缓存维护操作（Cache Maintenance Operations）必须同时作用于数据及其对应的内存标签。

B12.3 标签一致性
本节概述标签一致性的特性。
被缓存的分配标签由硬件保持一致性。一致性机制与数据一致性机制相同。
适用的标签缓存状态为 Invalid、Clean 和 Dirty。处于 Clean 或 Dirty 状态的缓存行为 Valid。
数据缓存状态与标签缓存状态之间的组合约束如下：
 仅当数据为 Valid 时，标签才能为 Valid。
 数据为 Valid 时，标签可以为 Invalid。
 缓存行处于 Unique 状态时，数据和标签均为 Unique。
 缓存行处于 Shared 状态时，数据和标签均为 Shared。
 当带有 Dirty 标签的缓存行被逐出时：
– 数据和标签均必须按 Dirty 处理。
– 标签必须写回内存，或者由 Home 节点以传递 Dirty[_PD]的方式传给另一个缓存。
 当 Clean 标签从缓存中被逐出时，可以将其发送到其他缓存，也可以直接丢弃而不发送通知。
 当 Clean 标签与 Dirty 数据一同被逐出时，Clean 标签可以随 Dirty 数据一起传输到 PoC 下游。

B12.4.1 TagOp 取值
当请求中的 TagOp 值为 Transfer 时：
 要求随数据一起返回标签。
 返回标签的状态必须是所使用请求允许的适当缓存状态。
 待返回的标签数量由返回的数据大小决定。
 当访问要求执行匹配检查时，由请求方将物理标签与随读数据收到的分配标签进行比较。
当请求中的 TagOp 值为 Fetch 时：
 要求随数据一起返回标签。
 返回的数据不要求有效。无论标签匹配结果如何，请求方都必须忽略接收到的数据。
 请求中的 Size 字段必须为 64B。
 必须返回一个缓存行对应的全部标签。
 返回标签的状态必须为 Clean 或 Dirty。
 如果返回 Dirty 标签，则必须保留这些标签（除非对其进行更新），并将其写回内存。
当请求中的 TagOp 值为 Invalid 时：
 允许但不要求随数据一起返回标签。
 如果随数据一起返回标签，则标签必须为 Clean。
B12.4.1.1 将标签从 Shared 转换为 Unique
当请求方同时持有处于 Shared 状态的数据和标签，并且为了更新数据、标签或两者而需要将缓存行转为 Unique 状
态时，预期使用 TagOp 值为 Transfer 的 MakeReadUnique 事务。也允许请求方使用 TagOp 值为 Transfer 的 
ReadUnique。
B12.4.1.2 已持有数据时获取标签
如果请求方持有某个缓存行的缓存副本，其中数据为 Valid，但分配标签不是 Valid，并且请求方要求执行 Tag
Match，则请求方必须使用读请求获取所需标签。
在上述场景中：
 如果请求方能够保证无论 Tag Match 结果如何都写入完整的缓存行，则允许使用以下任一种方式：
– 如果目标内存位置为 Non-snoopable，则使用 TagOp 为 Fetch 的 ReadNoSnp。返回的数据不要求有效，并
且必须丢弃。必须返回 Clean 标签。缓存行中的全部标签都必须为 Valid。
– 如果目标内存位置为 Snoopable，则使用 TagOp 为 Fetch 的 ReadUnique。返回的数据不要求有效，并且必
须丢弃。必须返回 Clean 或 Dirty 标签。缓存行中的全部标签都必须为 Valid。
 如果请求方不能保证无论 Tag Match 结果如何都写入完整的缓存行：
– 建议使用：

B12.4.1.3 允许的响应与标签状态
必须适当处理随分配标签一同收到的缓存行数据和状态，以免破坏一致性。
当请求的 TagOp 值为 Transfer 时，允许的响应字段取值为：
 Transfer：表示返回的标签为 Clean。
 Update：表示返回的标签为 Dirty。数据响应必须传递 Dirty[_PD]。
当请求的 TagOp 值为 Fetch 时，允许的响应字段取值为：
 Transfer：表示返回的标签为 Clean。
 Update：表示返回的标签为 Dirty。数据响应必须传递 Dirty[_PD]。
当请求的 TagOp 值为 Invalid 时，允许的响应字段取值为：
 Invalid：表示返回的标签为 Invalid。
 Transfer：表示返回的标签为 Clean。
当读数据中的 TagOp 值为 Invalid 时，TU 必须全为 0。Tag 不适用，可以取任意值。
在读事务中，当数据与响应分开发送时，TagOp 字段仅适用于 Data-only（仅数据）消息。TagOp 不适用于
Non-data（无数据）响应消息，且必须设置为 0。

B12.5 写事务（Write transactions）
用于支持 MTE 的不同字段分布在写事务的 Request 消息和 Data 消息中。TagOp 字段表示要对 WriteData 消息中
的标签执行的操作，Request 消息和 WriteData 消息中都包含该字段。Request 还包含 TagGroupID 字段，用于为
需要执行标签匹配（Tag Match）操作的请求所对应的通过/失败响应提供标识符。当 Request 中的 TagOp 字段为 
Match 时，Excl 字段必须为零。
注：TagGroupID 字段的具体用法取决于实现（IMPLEMENTATION SPECIFIC）。通常，可以使用 TagGroupID 来标识一
个响应所对应的异常级别（Exception level）和 TTBR。
WriteData 消息中的 TagOp 值通常与 Request 消息中的值相同，除非写数据已被侦听取走，或者写操作已被取消。
当 WriteData 与写请求中的 TagOp 值不同时，必须根据 WriteData 中的 TagOp 值来决定是否执行标签匹配。
WriteData 消息还为每个标签包含一个标签更新（Tag Update，TU）位。当 TagOp 为 Update 时，该位适用。
B12.5.1 允许的 TagOp 值
本节针对写请求消息中每一种允许的 TagOp 值，说明 WriteData 中允许采用的 TagOp 值。
当 Request 中的 TagOp 字段为 Invalid 时，WriteData 中的内存标签相关字段必须设置为 0，且完成方必须忽略这
些字段。

B12.6 无数据事务（Dataless transactions）

B12.7 原子事务（Atomic transactions）

 B12.9.2 转发侦听

B12.9.1 非转发侦听（Non-forwarding snoops）
当请求需要标签时，Home 节点可以使用任何适用的非转发侦听。如果侦听响应向 Home 节点返回了数据但未返回
标签，则 Home 节点必须先获取标签，然后才能向请求方返回数据响应。
Home 节点在响应 WriteUniqueFull、WriteUniqueFullStash、MakeUnique 和 MakeInvalid 时，不得使用
SnpMakeInvalid 侦听请求，除非满足以下任一条件：
 事务为 TagOp 值为 Update 的 WriteUniqueFull、WriteUniqueFullStash 或 MakeUnique。
 Home 节点能够确定被侦听方未持有 Dirty 标签。
注：请求方发送 TagOp 为 Fetch 的 ReadUnique，表示它将更新整个缓存行，但不更新标签。Home 节点不得使用 
SnpMakeInvalid 来响应该请求，以避免丢失被侦听方处已修改的标签。
Home 节点能够确定被侦听方未持有 Dirty 标签的一种情况是：最初向该被侦听方提供缓存行时，该行处于 SC 状态且标签
为 Clean。当 Home 节点将被侦听方跟踪为 Unique 状态时，不得使用 SnpMakeInvalid，因为被侦听方可能已在本地以
不通知 Home 节点的方式将标签变为 Dirty。
B12.9.2 转发侦听（Forwarding snoops）
只有请求不需要获取标签时，才允许 Home 节点使用转发侦听。即使被侦听方持有 Valid 标签，也允许发送转发侦
听。如果被侦听方在响应转发侦听时持有 Dirty 标签，则不得将 Dirty 标签转发给请求方，也不得将标签与数据的
Dirty 属性或 Unique 属性分离。
始终允许被侦听方向请求方转发 Clean 标签。
当标签为 Clean 时，被侦听方必须遵循与非 MTE 情形相同的数据传输规则。
当标签为 Dirty 时，被侦听方必须遵循以下规则：

B12.13 TagOp 字段使用汇总
以下内容汇总了不同通道的消息中 TagOp 字段的使用情况：
REQ 通道消息：
 Read* 和 MakeReadUnique 事务：
– TagOp 字段可以为 Invalid、Transfer 或 Fetch。
– 仅在 ReadUnique、ReadNoSnp 和 ReadNoSnpSep 事务中允许使用 TagOp Fetch。
– TagOp 字段的 Transfer 值指示是否必须随读数据一起返回分配标签。
– TagOp 字段的 Fetch 值指示仅要求返回有效标签。不要求返回的数据有效。
– 对于所有其他 REQ 通道消息，TagOp 字段不适用，并且必须为零。
译注：本段“其他 REQ 通道消息”的概括性表述在原文中重复出现，与下列具体请求规则及 B12.12 中 ReqLCrdReturn
等消息的任意取值规则并不完全一致。译文保留原文表述，使用时请结合具体事务条款核对。
 Write 事务：
– TagOp 字段可以为 Invalid、Transfer、Match 或 Update。
– TagOp 字段的 Transfer 值指示正在传输 Clean 标签，并且标签可以与数据一起被缓存。
– TagOp 字段的 Match 值指示需要对消息中的物理标签与该内存位置的分配标签进行匹配检查。
– TagOp 字段的 Update 值指示正在传递 Dirty 标签，必须使用这些标签更新分配标签的值。
– Exclusive 事务中不得使用 TagOp 字段的 Match 值。
 MakeUnique 事务：
– TagOp 字段可以为 Invalid 或 Update。
– TagOp 字段的 Update 值指示所有标签均被写入。
 Atomic 事务：
– TagOp 字段可以为 Invalid 或 Match。
– TagOp 字段的 Match 值指示是否需要进行标签匹配。
 StashOnce 事务：
– TagOp 字段可以为 Invalid 或 Transfer。
– TagOp 字段的 Transfer 值指示是否应将分配标签与 Stash 数据一起暂存。
 PrefetchTgt 事务：
– TagOp 值可以为 Invalid 或 Transfer。
 对于所有其他 REQ 通道消息，TagOp 字段不适用，并且必须为零。
DAT 通道消息：
 对于读数据，TagOp 字段指示随数据一起发送的分配标签是 Invalid、Clean 还是 Dirty。
 对于侦听数据，TagOp 字段指示在侦听响应中发送的分配标签是 Invalid、Clean 还是 Dirty。
 对于写数据，TagOp 字段指示写数据中发送的分配标签是 Invalid、Clean、Dirty，还是需要进行匹配检查。
TagOp 值必须与请求消息中的值相同，除非侦听已使标签状态降级，或者写操作已被取消。
