# 运行回归与交付验收说明

运行层负责把受控输入变成可追溯的构建、运行和结果。UVM负责协议、数据和系统行为检查。两者通过明确的参数和结果文件连接。

本模板以独立Python入口为主，现有ACVM或IP脚本可以封装为场地命令接入。真实命令及已实现选项以[模板运行说明](../template/docs_flow.md)和`python3 script/socflow.py --help`为准。

## 执行层级

| Profile | 运行含义 | 需要的外部条件 |
| --- | --- | --- |
| mock | Python模拟子进程和结果，验证工具链 | Python标准库 |
| uvm_selftest | 编译并运行synthetic UVM测试 | VCS或Xcelium、UVM 1.2、站点命令配置 |
| vip_selftest | 真实AXI master/slave VIP路径 | 已适配Synopsys接口、monitor与loader |
| cmn_bfm | BFM通过真实CMN访问内存 | CMN RTL、节点与路由配置、匹配协议VIP |
| n2_boot | N2通过CMN从DDR执行裸机 | CPU RTL、startup、镜像、启动和结果接口 |

模板对未接入的生产profile以及未实现的LSF/coverage能力明确返回BLOCKED。内网agent必须完成真实适配和验收后再开放；仅修改配置中的标记不构成实现。

## 配置的三个层次

设计配置描述地址图、组件存在性、接口和模型能力。构建配置描述filelist、工具、宏、参数、debug和coverage插桩。运行配置描述test、seed、镜像、激励参数和超时。

结构参数与宏会改变编译/展开结果；不能用运行参数改变端口结构。外部命令以argv数组记录，避免把未转义字符串拼成shell命令。公司已有环境初始化可以放在受控wrapper中，由其显式执行所需shell。

模板config生成器输出演示用SV/C常量，具体文件名见docs_flow。synthetic UVM自检有独立的小型测试地址范围；它没有自动接入目标SoC地址图。内网agent接入时应统一生成源，并删除重复手写常量。

## 一次运行的生命周期

1. 校验profile、test和能力需求，检查站点工具配置。
2. 冻结最终配置、seed、软件输入及构建输入身份。
3. 建立独立build/run目录，不覆盖旧目录。
4. 构建并检查实际产物；错误立即停止后续运行。
5. 启动本地进程或通过已验收调度适配器提交作业。
6. 收集进程状态、日志、TB结果以及必需软件结果。
7. 执行严格结果判定，写出机器可读结果和报告。
8. 保留复现信息；新一次尝试使用新目录。

第一版不依赖构建缓存。后续增加缓存时，key必须覆盖RTL/TB/include、生成文件、VIP/UVM版本、工具版本、编译参数、DPI及相关UPF/SDF。运行时独立加载的镜像作为run输入追踪；嵌入快照的镜像同时进入build key。

## UVM与runner接口

runner向仿真传入：

```text
+SOC_RUN_ID=<本次唯一标识>
+SOC_RESULT_FILE=<本次TB结果JSON绝对路径>
+SOC_SEED=<记录用seed>
+SOC_PROFILE=uvm_selftest
+UVM_TESTNAME=<测试类>
```

`SOC_SEED`是跨组件记录和校验字段，站点适配器还必须把seed正确传给仿真器原生随机种子选项。两者不能混淆。VCS和Xcelium同一个seed也不保证产生逐项相同的随机流。

TB结果schema版本为1，关键字段如下：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| run_id/profile/test/seed | string/string/string/int | 与本次manifest严格匹配 |
| status/completed | string/bool | TB最终状态与完成标记 |
| stimulus_count/checks_count | int | 实际执行与检查计数，正向自检不得为零 |
| pending_count | int | 测试结束时未处理事务数 |
| uvm_errors/uvm_fatals/assertion_errors | int | 错误计数 |
| software_required/software_status | bool/string | 是否需要真实软件及其结果 |
| failures | string array | 结构化错误ID |

只接受本次结果，不复用旧文件。必需软件能力来自profile/test契约，不能由TB自行改成不需要而绕过。未来增加字段时同时更新writer、validator、mock、单元测试和说明。

## PASS和预期失败

普通正向PASS要求进程正常结束、身份匹配、测试完成、必需检查执行、没有未处理事务、没有非预期错误、软件成功（适用时）、没有超时或取消。

软件PASS和TB PASS均不能覆盖进程崩溃。日志解析只补充识别仿真器原生错误或晚到错误；不能仅搜索字符串PASS，也不能把正常消息中包含error字样当作失败。

负向自检有精确的预期错误集合。原始run仍为FAIL，suite可以标注EXPECTED_FAILURE，表示检查链路识别正确。它与芯片业务测试通过分开统计。

## LSF接入契约

内网实现至少需要提交、查询、历史查询、取消和恢复收集五个操作。每个作业保存job ID、提交时间、队列、资源、工作目录、worker输入和终态来源。

调度系统报告DONE表示作业执行完成，不能单独证明验证通过。EXIT、取消、资源超限、节点故障和未知状态分别保留。查询暂时没有结果时继续核对历史，不能推断成功。提交返回不明确时先查重，避免重复提交。

超时至少分为排队/许可证等待、真实运行时间和仿真时间。停止本次回归只取消其拥有的作业。worker退出时保留仿真真实退出码，并记录信号或超时原因。

未在真实集群验证这些路径前，模板不开放生产LSF执行。

## 覆盖率和测试计划

代码覆盖、功能覆盖、断言触发和需求覆盖分别管理。覆盖率证明激励触达程度，正确性仍由检查器判定。

VCS和Xcelium数据库不直接混合。合并前校验工具版本、设计配置、层次、覆盖插桩和covergroup定义。不同配置的需求完成情况可在报告层汇总，不能随意合成一个数据库百分比。

失败运行覆盖率保留用于诊断，签核纳入规则单独定义。模板中的覆盖率合并入口若未完成适配，应明确拒绝执行。

## 复现的边界

保存seed和命令只是复现的必要条件。还需相同源码与未提交修改、相同工具/VIP、镜像、生成配置和可影响行为的环境信息。模板重跑使用保存输入和新目录；若依赖已经改变，应报告差异或阻止“原样复现”的声明。

## 软件镜像链路

镜像准备工具和C接口说明见[软件接口与镜像装载](../template/native/README.md)。工具输出PT_LOAD段、hash、装载地址与零填充长度；真实memory service仍需把它们写入VIP backing store并验证。

工具成功不能证明CPU能从该地址启动。CPU reset vector、ELF入口、装载物理地址、cache/MMU以及访问属性需要联合核对。

## 内网验收证据

每个阶段记录：工具版本、源码状态、配置、真实命令、seed、返回码、日志、TB结果、报告、波形或必要观测。先运行小型正测和注错，再扩大回归。测试计划详见[验收矩阵](06_测试计划与验收矩阵.md)。

本地Python检查的实际结果和未执行项统一写入交付包的验证记录，避免将工具链自检和EDA仿真混在一起。
