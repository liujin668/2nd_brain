# 内网 Agent 实施任务书

你的任务是在内网已有 IP 验证工程的基础上，建立可执行、可检查、可回归的单 die 服务器 SoC UVM 环境。使用本交付包的方案与模板作为参考，并根据真实 RTL、VIP 和工具完成适配。现有 ACVM 可以接入，也可以使用独立脚本；不要求保留某个框架名称。

## 已确认条件

- CPU 计划使用 Arm Neoverse N2，当前外部方案阶段尚无 RTL。
- 互连为 Arm CMN，具体型号、协议版本、拓扑和内存出口需要内网确认。
- 首目标是最小系统冒烟，不启动操作系统。
- DDR 可先由匹配实际出口协议的 memory VIP 替代。AXI memory VIP 只在接口匹配时使用。
- 期望 UVM 预装载镜像，CPU 从 DDR 地址启动。真实 reset vector、访问属性和保持条件必须根据 IP 集成要求落实。
- 工具为 VCS、Xcelium、UVM 1.2、Synopsys VIP 和 LSF。
- 已有可运行 AXI master/slave VIP 示例，现有工程包含 env、tb/hdl_top、tb/hvl_top、native、test、regress 和 script。
- 已有 CA55 C 编译组只能作为流程参考，不能改名字后视为 N2 启动支持。

## 先读哪些文件

先阅读交付包 README，再阅读总体架构、组件设计、运行回归和本任务书。然后读取 template/docs_sv.md、template/docs_flow.md 及相关代码。以实际源码和 --help 输出核实命令，不把说明中的未来功能视为已经实现。

本包含三类材料：设计目标、实际模板实现、尚待接入的扩展契约。请在你的实施记录中继续区分它们。

## 第一阶段 盘点现有工程

遵守现有仓库的工程规范，检查工具启动环境和已验证的示例，不修改服务器系统库。记录以下信息到你生成的 inventory.md：

| 输入 | 必须确认的内容 |
| --- | --- |
| 仿真器 | 实际版本、UVM 来源、编译/展开/运行命令、波形和断言开关 |
| VIP | 交付版本、协议支持、接口参数、内存后门 API、monitor/响应通道、reset 语义 |
| 工程结构 | 真正 top、各 package 的 include 归属、完整 filelist、生成文件来源 |
| 时钟复位 | 外部引脚、极性、初态、同步责任、时钟域和冷/热复位影响 |
| DUT | 已有 RTL、缺失 IP、wrapper 端口、地址译码与安全属性 |
| 软件 | 可用交叉编译器、ELF 格式、启动入口、链接脚本、结果和日志通道 |
| LSF | 队列、资源表达式、作业状态/历史查询、取消机制、共享目录和许可策略 |

可独立推进的组件继续实现。只有影响真实接入的关键事实缺失时，向工程负责人提出具体问题；不要通过猜测 CMN 型号、引脚名或 VIP API 消除问题。

## 第二阶段 验证工具链结果判定

先执行 Python 工具链自检和镜像工具单元测试。mock 运行只证明脚本行为。

必须检查：正常退出、非零退出、超时、缺结果、旧 run_id、错误测试名、零激励、零检查、未排空事务、成功标记之后的错误、错误软件状态。负向自检的原始 run 仍保存失败，suite 只能额外标注“预期失败被识别”，不能篡改为业务 PASS。

保存执行命令、返回码和报告。若修改结果 schema，同步更新 SV writer、Python validator、mock、文档和测试，不允许只有一端更新。

## 第三阶段 编译 UVM 自检

按真实工具版本补 site 配置或 wrapper，指定唯一 top，使用一种 UVM 1.2 来源。先做 VCS 编译/展开，再做 Xcelium 编译/展开，分别保存日志。

完成 soc_selftest 正测和 soc_selftest_mismatch 注错。确认 clk/reset handshake、SVA bind 实例、结果 JSON、test identity 和错误传递。解决任何类型、包依赖、时间单位或接口参数差异。

纯事务层 selftest 不构成 AXI driver/monitor、CMN 或 CPU 验证。不要通过删掉 mismatch 检查、降低 severity 或关闭断言来获得通过。

## 第四阶段 接入真实 AXI VIP

从已跑通的 Synopsys 示例提取 wrapper、配置和编译规则。最初保持相同接口参数，逐项改成目标配置。

接入以下能力：

1. Master 请求及完成状态。
2. Slave memory backing store 的装载、读出、初始化和复位行为。
3. 基于实际握手的独立 monitor；不能只复用 sequence 已发送的内容。
4. VIP 协议错误向统一结果服务的传递。
5. Byte enable、burst、并发 ID、合法乱序与背压检查。
6. 请求到完成的追踪、超时和复位代次。

按测试计划执行读写、预装载前门读回、部分写、边界、背压和注错。在验收前保持 vip_selftest 为未接入状态；完成 adapter 和证据后再解除阻塞。禁止只改 profiles 中的标记而保留空 adapter。

## 第五阶段 接入 CMN

确认请求节点类型、CHI 版本、Node ID、地址归属、系统缓存、内存出口协议以及启动配置方法。若出口是 CHI，选择相应 subordinate VIP 或保留真实桥，不自动假设 AXI。

先用受控、无歧义的非冲突流量验收路由和数据，再增加并发、重试、冲突和一致性。简单内存模型不能给复杂缓存事务提供全局可见顺序的唯一预期。优先使用与配置匹配的成熟一致性检查组件。

## 第六阶段 接入 N2 裸机启动

落实 CPU RTL 的 filelist、复位和初始化要求，选择一个核心作为启动核心。其他核心如何保持或释放以实际集成规范为准。

验证顺序是：模型 ready、镜像分段装载及零填充、装载后读回、必要的 fabric 配置、启动入口稳定、CPU 启动条件释放、取指/进展证据、软件结果、最终硬件检查。

分别处理 ELF 虚拟入口和物理装载地址。镜像入口不自动等于硬件 reset vector；确认 boot ROM、RVBAR/复位入口、异常级别、地址映射和对齐约束。cache/MMU/屏障必须具有明确的平台实现。

软件完成结构应有 run token、test ID、版本和初态；使用非缓存结果区或正确的可见性维护。软件 PASS 后还需要排空相关事务、检查协议、scoreboard 和 assertion。

## 第七阶段 LSF 和回归接入

本模板的 LSF 未接入时应返回 BLOCKED。补齐提交、job ID 持久化、运行状态、历史查询、取消、超时、恢复收集和异常分类后，才允许正式批量运行。

至少验证队列等待、许可证等待、正常完成、程序失败、运行超时、调度终止、节点故障/失联和 runner 重启后的恢复。提交结果不确定时先核对是否已有作业，避免重复提交。

从固定 seed 的小型 smoke 开始，再增加多 seed 和 nightly。VCS/Xcelium 的 coverage 数据库分别管理，仅合并已确认兼容的同类数据；完整测试计划中要单列不支持、未执行和豁免项。

## 实施中的强制一致性规则

- 宏、结构参数和运行配置分开；更改编译输入需要新的构建标识。
- 模块、interface、package、class 的归属唯一；不同时 include 和独立编译同一 class。
- 实际 clock/reset 信号只有一个 owner，UVM 通过控制接口发请求。
- 不用 TB 强制内部复位或内部状态来掩盖设计本应实现的功能。
- 每个 checker 说明检查对象、采样点、启用窗口和错误 ID。
- 没有设计规格时保留明确待定项，不发明 expected value。
- 缺 checker、空场景、缺软件完成、异常退出不能 PASS。
- 用单独的 run 目录保存每次尝试，不覆盖失败现场。
- 不在实现报告中把 mock、静态检查或编译通过称为真实 SoC 验证通过。
